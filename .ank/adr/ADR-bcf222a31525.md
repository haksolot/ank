## Context

Ank coexists with git without duplicating it. The question here is what happens
when several agents work on parallel branches.

Two properties already hold without changing anything, and they should be
preserved rather than reinvented.

Claims live in `refs/ank/claims/<id>` (ADR-4e7c25b1f639), and a ref belongs to no
branch: it is global to the repository. Coordination therefore does not fragment
when branches diverge, and git's compare-and-swap separates two agents whatever
branch they work on.

The flat tree with one file per entity further means parallel creations never
conflict: two agents each creating three tasks produce six distinct files. Only
simultaneous modification of the same entity conflicts, and the claim makes that
rare.

## Problem 1 — the window of lost work

The claim ref is deleted at `done`, but the `done` itself is visible only on the
branch of the agent that produced it. Between the end of the work and the merge
of that branch, the task looks free everywhere else: another agent runs
`ank context`, reads `open`, and can claim work that is already done.

The window is not marginal — it lasts as long as a PR review, which is most of a
branch's life.

The fix stays inside the ephemeral coordination plane, touching nothing in
durable state: instead of deleting the ref at `done`, we turn it into a
completion ref pointing at the commit, with no TTL. It is pruned only once
durable state has caught up with the information the ref carried. The ephemeral
ref then lives exactly as long as it is useful, which is the definition we gave
it.

`claim` can then answer precisely: task finished on another branch, commit
`abc1234`, not merged here yet.

## Refinement over the submitted wording

The original wording mechanised pruning through the reachability of the recorded
commit from the default branch. That is the right criterion in intent and the
wrong one in practice, because `done` writes only to the working tree (§12): the
commit it can record is the current HEAD, which does not contain the
`status: done` that was just written. An agent that branches and then runs `done`
before its first commit therefore records a HEAD that *is* already the default
branch — the ref would be pruned within the second, which reopens exactly the
window the mechanism closes.

The predicate retained is the one the "that is to say" clause of the original
wording already stated: the task appears `done` or `closed` on the default
branch. It is read with `git cat-file -p <default_branch>:.ank/tasks/<id>.md`, it
is true exactly when durable state has caught up, and it is insensitive to the
order in which the agent commits its code and its task file. The recorded commit
stays in the record, for `claim`'s diagnostic; it no longer decides pruning.

## Problem 2 — accept on a feature branch

`accept` produces a signed commit that makes a constraint binding, but only on
the branch where it runs. That yields a constraint of variable geometry, and the
ratification hash becomes dependent on the reading context — exactly the
ambiguity Ank eliminates everywhere else.

The legitimate use case (introducing a constraint and the code that applies it in
the same PR) is already covered by the model: the ADR is created in `proposed` on
the branch, travels with the code, and is accepted only once on the default
branch. An unratified constraint binds nobody, so nothing is lost by waiting.
That is why the prohibition is strict: no `--force`, which would become the
default path within two weeks.

The default branch is read from `default_branch` in `config.yml`, with detection
through `refs/remotes/origin/HEAD` as a fallback and an explicit error if neither
answers.

## What this ADR does not do

It does not address state divergence between branches. An agent on a
three-day-old branch sees that branch's constraints, not the ones accepted since.
That is the classic stale-branch problem, and the answer is the same as for code:
rebase. The hash of applicable constraints recorded at claim time already covers
the case — if the agent integrates the default branch mid-course, `done` warns
that the constraint field has changed.

It does not replace ADR-4e7c25b1f639, it complements it: where claims live does
not change, only their lifecycle.

It does not give `close` a completion ref. A task closed on an unmerged branch
carries the same invisibility window as a finished one, but `close` is a human
act and a rare one, and the pruning predicate already accepts `closed` — the gap,
if it shows up, can be fixed without touching the format.

## Alternatives rejected

**Relying on the file's `status: done`.** That is already the case, and it is
precisely what does not suffice: the status lives in durable state, invisible to
other branches before the merge.

**One claim per branch.** Would destroy the property "one piece of work, one
holder": two agents would do the same task twice, each of them legitimately.

**A distinct ref namespace for completions.** Would let a stale claim and a
completion coexist for the same task, which is the ambiguity the ref exists to
settle, and would split the compare-and-swap across two addresses where there is
only one conflict. The state is therefore carried by the record, not by the
address.

**A daemon centralising state.** Contradicts levels 0 and 1, and is not in the v1
scope.

## Consequences

On the specification, §7: describe the full lifecycle of the ref (pickup,
completion, pruning) instead of "deleted at done", and add `default_branch` to
`config.yml`. On §4: `accept` gains its branch precondition in code 7, and
`claim` an extra refusal case in code 4. On §12: the plumbing widens, which
ADR-b8884edcebe3 carries.

On the tasks: TASK-c3d4e5f6a7b8 carries the ref lifecycle, TASK-a7b8c9d0e1f2
carries `accept`'s precondition and the pruning by `check`. Neither is claimed at
the time this ADR is written, so their `done_criteria` can be amended with no
freeze to lift. Resolving the default branch, on the other hand, falls into
`config.rs` and `git.rs`, whose task is `done`: it yields TASK-038c83ba44c5, a
new task and not a reopening (§3).
