constraint: |
  Every format change happens in this order: the specification first, then
  the golden files, then the code. The round-trip is byte-identical on
  canonical form; valid but non-canonical input is read correctly and
  normalised on first rewrite. CRLF line endings are read, never written. No
  field exists in the code without existing in the specification.

Replaces ADR-9d4b7e2a5c13 rather than amending it: `constraint` is locked on an
accepted ADR (§3), and the fact that the bootstrap ADRs have no ratification
commit would make the edit undetectable rather than legitimate. This is exactly
the case ADR-6b3f19e08a24 describes — the absence of an anchor does not create a
permission.

The original wording, "the round-trip must stay byte-identical", was true but
incomplete, and the incompleteness was turning into a contradiction. A file in
CRLF is valid format written by a legitimate third-party tool — git itself, on
Windows, with `core.autocrlf` at its default value. Reading it correctly and then
rewriting it in LF is the intended behaviour, and it violates the letter of the
original constraint.

The canonical / non-canonical distinction already existed in the implementation
for the other acceptable YAML forms; it simply was not written down. What is
decided here is therefore not a relaxation but the writing down of what "the
format is the specification" required from the start: a third-party tool must be
able to write without knowing the canonical form, without that form becoming an
authoritative variant.
