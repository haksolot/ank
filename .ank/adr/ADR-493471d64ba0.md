## Context

`done` and `attest` write into the working tree, and section 12 forbids ank from
committing anything except the signed ratification. So the only way a CI run can
be recorded against a task today is for somebody to commit the edited file.

That is the wrong shape for the fact being recorded. A green pipeline is a
statement about a tree, produced by an environment nobody working on a branch
controls — which is exactly why section 4's trust hierarchy ranks `test:ci://`
above a local run. Requiring that statement to arrive as a commit on somebody's
branch puts the most trustworthy proof behind the least trustworthy delivery
mechanism, and in practice means it never arrives: this corpus carries ten `done`
tasks with no test proof, each one a run that went green and was never written
down.

## The category this admits, and why it is named

Section 7 separates two planes: durable state in files, ephemeral coordination in
refs. A proof is durable, so on the letter of that split it belongs in a file.
This ADR does not blur the split; it names a third thing the split did not
anticipate.

**External attestation** is durable, and it is produced by an actor with no
branch. That is the whole of it. Durable state is authored by whoever is doing
the work, travels with their code, and is arbitrated at merge like any file.
Coordination is disposable and belongs to nobody. An attestation is neither: it
must survive, and it has no tree to travel in.

Refs are the right home for exactly that reason, and the machinery already
exists. `refs/ank/proof/<task-id>` is one ref per task, so two pipelines
attesting two tasks never contend; the record is a blob written the way a claim
record is written; the push is the same `--force-with-lease` compare-and-swap.
Nothing new is invented, which is the argument for it.

## Why the union has to be symmetric

The temptation is to treat the file as authoritative and the ref as a cache.
Resisted, because it is false in the direction that matters: between a `done`
landing on a branch and its merge, the ref is the only place the CI reference
exists, and that window is most of a branch's life. A reader that prefers the
file would show an unanchored task and a signal telling someone to attest work
that has already been attested.

So both are read, both are shown, and the display says which is which — a
detached proof lives outside the tree, and a reader deciding how much to trust it
needs to know that without being told to prefer it.

## Rejected

**git notes.** `refs/notes/ank` is the idiomatic git answer to attaching data to
a commit without rewriting it, and it is the wrong primitive here. A note is keyed
by the object it annotates; a proof is about a *task*, which may be attested long
after the commit that finished it, and by a run that tested a merge commit the
task never saw. Keying by task is what the existing refs already do.

**Letting the CI commit.** It works, it is what everyone does, and it means the
pipeline needs write access to the branch, a bot identity, and a rule to keep the
resulting commit from re-triggering itself. That is a lot of moving parts to
record one line, and every one of them is a thing that can be misconfigured into
a corpus that lies.

**A `--proof-ref` flag on `done`.** `done` runs the verifiers itself and records
what it ran; it is not the verb that carries somebody else's result. `attest` is
already defined as the one write allowed after `done`, which is precisely this.

## Consequences

The refspec `+refs/ank/*:refs/ank/*` that `init` installs already fetches this
namespace, so an existing repository needs no configuration change.

A repository with no remote gets a local ref and no arbitration, which is level 0
behaving as it always does. The pipeline case implies a remote by construction,
so the degenerate case is not the one anybody meets.
