§6 gives `find` lexical search through FTS5, and TASK-f6a7b8c9d0e1 shipped a
scan instead. The substitution is recorded here rather than left silent: over a
corpus of thirty entities the difference is unmeasurable, and the criterion that
task carried was about the cap and the announcement of what was cut, not about
the mechanism. Neither of those changes here.

What a scan actually costs is one file read per candidate, because the index
holds titles and scopes but not criteria or constraints — so a query on the text
that carries the meaning opens every entity. That is the line this task moves,
and it is why the criterion above is written in terms of a thousand entities
rather than in terms of using FTS5.

The schema version added by TASK-b2c3d4e5f6a7 is what makes this cheap: an index
of an unknown schema is wiped and rebuilt, so adding a virtual table is a rebuild
and never a migration. `rusqlite` needs its `fts5` feature for the table to
exist, which is a feature flag on a dependency already present, not a new one.

Scope gains `crates/ank-cli/Cargo.toml` before the claim, criterion untouched:
that feature flag is the one thing standing between the criterion and a table
SQLite refuses to create, and the manifest is where it lives.

**The paragraph above is wrong about the feature, and the correction is worth
more than the claim was.** There is no `fts5` feature on rusqlite 0.40 to
enable; asking for one fails to resolve rather than being merely redundant.
FTS5 is already in the binary, because `libsqlite3-sys` compiles the
amalgamation with `-DSQLITE_ENABLE_FTS5` whenever `bundled` is on. So the
manifest changed only to record that, and the dependency set is untouched. The
original reasoning is left standing above rather than rewritten: it was the
honest expectation at the time, and what it got wrong is the useful part.

**One behavioural difference from the scan, and it is not an accident.** FTS5
matches tokens, so `find` is now prefix search rather than substring search:
`canonic` finds "canonical", and `rlf` no longer finds "CRLF" the way a
`contains` did. That is the lexical search §6 asks for by name, and the reason
the criterion could be written in terms of a thousand entities at all — a
substring match over tokenised text is not something an inverted index can
answer. Recorded because someone will eventually search for an infix and find
nothing.
