Today (done.rs, run_verifiers) verifiers start in declared order, and the
failure reported is the first *in declared order*: a verifier declared before
a failure is waited for, because it could still change the answer
(TASK-26eab418555a). That keeps the answer identical to a sequential run, and
it makes a cheap failure wait for an expensive verifier declared before it.

This task changes that property on purpose: the failure reported becomes the
first in time, and execution order becomes cheapest first. It is the one place
in this plan that changes an answer `done` gives. No ratified ADR states the
declared-order answer (it lives in TASK-26eab418555a's criterion and a code
comment), so the change needs no supersession, but the reviewer should see it
stated here. If the maintainer wants it kept, release with that reason and
the task shrinks to cheapest-first ordering with declared-order reporting.

## Kill or let run: decided by measurement, not here

Killing the other verifiers at the first failure makes the failing `done`
return sooner, and a killed verifier has no answer, so nothing is recorded for
it: the `done` that follows the fix reruns it in full. Letting them finish
makes the failing `done` slower and records their passing runs, so the next
`done` reuses them. Which costs less over the fail-fix-retry cycle that is
the loop's common case is a number, not an opinion. The criterion therefore
asks for the measurement first, in this task's log, and binds the binary to
the policy with the lower total; its tests assert whichever was chosen.

Cost is the duration of the most recent recorded run of a verifier of that
name, whatever its key, read from the local registry (ADR-a2faf59f6ce0, which
already holds the entry). No cost is declared in config.yml: a declared cost
goes stale, a measured one does not. Unknown cost sorts after every known one,
in declared order. Ties keep declared order.

Unchanged and binding: the lock of ADR-eab130f731f3, a killed verifier
recorded as nothing, exit 9 never recorded.

Waits on TASK-06f91cff057e: if the measurement shows one verifier dominating
and no failure pattern a reorder would shorten, this is the task to release.
