Measured by reading `ank help` after the specification became entities of the
corpus. The listing says:

    ank scope <path>   what covers a path: the constraints that bind it and the
                       tasks that touch it

and the verb prints three groups — `ADR`, `SPECIFICATIONS`, `TASKS`. Checked on
`crates/ank-core/src/parse.rs`: 10 ADRs, **3 specifications**, 15 tasks. The
description enumerates two of the three, so a reader learns that `scope` answers
about rules and work, and does not learn that it is the verb that says which
specification governs a file.

That matters more than a missing word normally would, because `scope` is one of
the two verbs the investigation mode was added for (ADR-5dd7b4a9c875), and
finding the document that governs a perimeter is precisely what an agent reaches
for it to do.

**It is the defect §9 already legislates against, in a shape the existing test
does not catch.** The rule there is that a description is a fourth surface able
to misinform, and the test that enforces it walks *flags*: it fails when a
description advertises a flag the verb does not offer. Nothing compares a
description that enumerates the verb's **output** against what the verb emits,
and this description enumerates output. The test the criterion asks for closes
that: read the headings from the verb, read the description from `help`, and
fail when the first names a group the second does not.

One thing to settle while here rather than in passing: **whether `find`'s
description should name `--type`.** It names `--status open`, because listing
what remains with no query is an idiom worth surfacing; `--type spec` is now the
route to the specification and has the same claim to being one. The per-verb
page already carries the flag, so this is a question about the listing alone,
and it is a judgement rather than a defect — decide it, and say which way in the
task's log.
