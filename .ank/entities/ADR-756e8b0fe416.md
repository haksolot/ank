## Context

Nothing in a corpus says which ank it needs. Every entity carries a `schema`
(1 to 4 coexist in this corpus: 4, 13, 309 and 981 files, measured
2026-10-24), and a binary reads every older schema, so an old corpus under a
new ank is a healthy state. The other direction is announced only after the
fact: `schema_ahead` warns once a file newer than the binary has landed, at
which point its entities are already left out of every listing. Two people
on one corpus can run two binaries, and nothing tells the older one before
it misses something.

`ank update` exists and is the only verb that reaches the network
(ADR-64f32c74a0f9 keeps it that way), so a comparison has to be against the
running binary's own version, never against the latest release.

The maintainer decided on 2026-10-24: a minimum version, moved by a human,
warned on every verb and counted as a fault by check, with config.yml moving
to schema 2.

## Decision

1. **`requires_ank`**, an optional key of `.ank/config.yml`, holds a version of
   the exact form `MAJOR.MINOR.PATCH` and means "this ank or newer". Any other
   form is refused when the file is read, naming the key. Absent means no
   requirement.
2. **It is compared with the running binary's version**, component by component
   as numbers, the rule `ank update` already applies to tags. No verb reaches
   the network for it.
3. **Below the requirement, every verb warns and goes on.** On stderr, outside
   any `--json` document, silenced by `--quiet`, in the shape of the
   schema-ahead warning: the declared and the running version, and `ank update`
   as the next step. At or above it, nothing is printed.
4. **`ank check` reports it as a fault**, so a pipeline running an older ank
   turns red instead of checking a corpus it may misread.
5. **A human moves it.** `ank init` writes the running version; `ank config
   requires_ank <version>` raises or lowers it; no other write changes it.
6. **The configuration moves to schema 2**, and the reader accepts 1 and 2. A
   file carrying `requires_ank` declares 2, so a binary that predates the key
   says the file is newer than it and how to replace it, rather than refusing
   an unknown key as if it were a typo. A file without the key may stay at 1.

## Consequences

- Binaries up to 0.9.2 refuse a schema-2 configuration outright. That is the
  intended outcome: they cannot honour the requirement, and the refusal names
  the remedy.
- This repository can declare the key only once a release that reads schema 2
  is published, since its own tree build carries the version of the last
  release until the bump.
- The format reference (docs/config-keys.md) is generated from the reader and
  changes with it.

## Rejected alternatives

- **An exact pin.** Forces a pull request on every release for no format
  reason; a newer binary reads an older corpus by construction.
- **Raised by every write.** One up-to-date collaborator would force the whole
  team to update although nothing in the format changed.
- **Refusing below the requirement (exit 9).** Blocks reading too, where the
  schema-ahead precedent degrades and names the remedy.
- **Keeping schema 1.** Older binaries would report `unknown key requires_ank`,
  which reads as a typo and names no remedy.
- **Comparing with the latest release.** Would put the network on every verb,
  which ADR-64f32c74a0f9 forbids.
