## Context

LOG-879c2ce798a1, written while implementing the read half of ADR-a1de673043b4,
keeps peer constraints out of execution mode on purpose: the claim freezes the
hash of the rules it serves, and a rule whose home is a corpus `refs/ank` cannot
reach has no place in a freeze, because the hash would move when a sibling
checkout changed and `done` would warn about something nobody here could show.

The reasoning about the freeze holds. The conclusion does not follow from it.
Measured on 2026-10-26 at e04c0dad: in `web`, `ank context src/` lists
`ADR-71f0e88947fb@api` with no claim; once `exec1` claims a task scoped `src/**`,
`ank context src/` serves the local ADR and **not** the peer's. The agent that
writes the code a cross-repository decision governs is the only one never told
about it. In an orchestrated cycle, the orchestrator sees the rule in
orientation and the executant it dispatches does not.

## Decision

Showing and freezing are separate. A peer constraint is **shown** to the
executor, in its own section, labelled with the peer and the commit of its
default branch that was read (ADR-09b985a5627e makes that commit well defined).
It is **not frozen**: the claim's hash covers the local rules exactly as it does
today.

What the freeze bought for local rules, a statement at close that the ground
moved, is kept by recording rather than by hashing: the claim stores the peer
commit and the hash of each peer constraint served, and `done` names any that
was added, changed or retired since, then closes as it would have. It never
refuses on it: a merge in another repository is not this executor's fault, and
it is a fact the reviewer of the close should read.

## Rejected

- **Freeze peer constraints into the claim.** A merge in the peer would make
  every open claim in the reader report an alteration nobody here made.
- **Leave execution mode as it is.** Measured above: the rule does not reach the
  agent it binds.
