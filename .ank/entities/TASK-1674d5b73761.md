Measured on 2026-08-16, on the publish-apt run that a re-published v0.3.0
produced (run 31988635022). The build job was green -- the pool was assembled
from the releases, signed with the real key, and the tree uploaded. The deploy
job failed in two seconds, before any step ran, with an annotation and no log:

  Tag "v0.3.0" is not allowed to deploy to github-pages due to environment
  protection rules.

A `release` event runs at the ref of the tag it published, and the `github-pages`
environment carries a deployment branch policy that admits branches and not this
tag. So the one event the channel exists to serve is the one event that cannot
publish, and the failure is invisible until a release actually happens: every
other trigger either skips the deploy or runs from a branch.

v0.3.0 was completed by dispatching publish-apt from main, which the workflow
supports on purpose -- its own comment argues that a dispatch publishes what a
release would have published and nothing else, because the tree is a function of
`gh release list` and not of the ref. That is why this cost nothing this time, and
it is also why the gap survived: the dispatch path is exercised often and the
release path had never run.

Two ways to close it, neither measured. Add a tag rule to the `github-pages`
environment so `v*` may deploy, which is a repository setting and therefore a
thing no file in this tree records -- the reason it should be argued rather than
merely clicked. Or give the deploy job a branch ref, by having the release event
hand the version to a run that checks out the default branch, which keeps the
policy as narrow as it is now.

Blocked on TASK-2078ab116f63 only in order of measurement: while a published
release starts no publish-apt run at all, this criterion cannot be observed on a
tag without republishing one by hand.
