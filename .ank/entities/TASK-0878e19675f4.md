Found by the agent that closed TASK-f067ae7c84ff, reported on that task and not
fixed there. The repair it landed defers the refspec into `ank-origin.config`,
included under `includeIf.hasconfig:remote.*.url:**`, so the condition is false
while no remote has a URL and `git remote add origin` sees no `origin`.

The condition is on `remote.*.url` and not on `remote.origin.url`, because that
is the only key form git's `hasconfig` supports. So any remote with a URL turns
the include live. Run `ank init` in a repository with no remote, add `upstream`
first, and `remote.origin.fetch` becomes visible again with no `origin`
configured: `git remote add origin <url>` refuses exactly as it did before
TASK-f067ae7c84ff, and `ank status --remote` again names a command that fails.

The neighbouring state is already handled and is the model for this one: a
repository that has remotes but none named `origin` at init time gets nothing
written, which leaves `git remote add origin` working, and re-running `ank init`
once `origin` exists writes the key directly. What is missing is that the same
reasoning has to hold when the other remote arrives *after* init rather than
before it, and the include cannot express it.

Repos initialised by a binary older than TASK-f067ae7c84ff keep the old key and
are not migrated; that is a separate question and not this task's.
