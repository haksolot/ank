Issue #810, reproduced on 0.9.4 (ff25eecb): with a leftover local ratify ref
that does not match, `accept` fails at `git update-ref` with
`error[9]: ... cannot lock ref ... reference already exists`, and the ADR is
stuck until the ref is deleted by hand, on the remote too.

Measured in the same session: with a *valid* local ref (an earlier accept whose
file write was undone and whose push was removed), `accept` succeeds, but writes
a new tag object (bec1eb7 then f82452c). That discards the first ratification,
possibly a signed one; the criterion asks that it be reused instead.

Decided with the maintainer: a non-matching ref is refused, never overwritten.

Still open from the issue: how the first run kept its tag without completing.
`help accept` promises nothing is kept when the tag or the push fails. Worth a
log entry if the diagnosis finds the path.
