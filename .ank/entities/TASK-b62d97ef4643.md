A proposal, not a change. The maintainer decides which moves to make; each one
becomes its own task against the workflow files.

What is already known, from PR 853 (task files only): the Install workflow
(.github/workflows/install.yml) ran on five runners, triggered by
`pull_request` with no paths filter. As `gh pr checks 853` showed them: ubuntu-24.04-arm 48s,
ubuntu-latest 56s, macos-latest 1m0s, windows-latest 1m31s, macos-15-intel
2m24s. The last one is outside the 50 to 90 s range first reported, so the
task re-reads these from the logs rather than taking them from here.

The regression side of each move is the half that matters: a job moved off
pull requests still runs, but on main, after the merge, where a red goes
unseen (see the attest race and the main-CI incidents in this corpus's
history). A move is worth proposing only when the regressions it lets through
are rare in this repository's own record, so the record is read, not
imagined. macOS Intel is the known case: release.yml builds it and CI does
not, and it has caught a real race before.

Reading CI logs through gh is fine for the measurement; what must stay
forge-free is the binary (ADR-9a0076dd0896's fourth property, as carried by
ADR-89c1e7146fe5). Workflow files are integration, outside the core.
