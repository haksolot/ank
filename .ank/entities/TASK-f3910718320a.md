Measured on TASK-f113addd8f40, and the pipeline is what found it. `ank log`
recorded a message holding a lone carriage return, `ank check` said the corpus
was healthy, and the `line endings in .ank/` guard of `ci.yml` refused the
branch on all three runners: the CLI wrote a corpus its own pipeline rejects,
and the only reader that noticed was the one outside the tool.

The blob: 738 bytes, two line feeds, one carriage return. One CR for two LF is
not a CRLF pair -- it is a lone CR inside the text of an entry. That is why
`.gitattributes` did not catch it either: `.ank/** text eol=lf` normalises CRLF
to LF on commit, and a lone CR is not CRLF, so it passes straight through.

Where it came from is worth writing down, because it is not the failure mode
one would guess. It was not a multi-line message whose `\r\n` lost its `\n` to
the record separator. The message was one line, handed to the binary from
PowerShell inside a double-quoted string, and it contained the word
`` `rev-list `` -- a backtick, which PowerShell reads as its escape character,
followed by `r`. `` `r `` is PowerShell's carriage return. The shell expanded
it before the binary ever saw an argument, and what `ank log` received was a
message with a CR in the middle of it.

So the entry point is not exotic: any caller text that reaches a log line can
carry a control character, and a shell is entitled to put one there. The write
side accepted it without a word, and the read side agrees -- `parse_log_file`
splits on `\n` only, so the line parses, the CR stays in `message`, and
`LogEntry::format_line` writes it back out. The round-trip is faithful to a
byte that should never have entered.

**Refused rather than stripped, and this is the decision the criterion
freezes.** Ank is not a gatekeeper about *content* (ADR-6b3f19e08a24): it
records what a caller states, including a proof it cannot verify. A control
character is not content -- it is a shell accident the caller did not type, and
silently deleting bytes from a message somebody wrote is a worse answer than
saying which byte is wrong. `log_write` already refuses an empty message with
exit 1 and the command to run again; this is the same door, and the message
should name the character by its escape so that the reader who typed a backtick
in PowerShell can see what happened.

**At the one place an entry is built, not per verb.** `log` is where it was
measured, but `done`, `attest` and `release --reason` all turn caller text into
a log line, and a check written into one of them is a check the next verb will
not have. `LogEntry` in `crates/ank-core/src/log.rs` is the single door every
one of them goes through, and the format is the specification.

What this does not touch: the corpus already carries such an entry on
TASK-f113addd8f40, repaired on its branch before the merge. Nothing here
rewrites history, and a rule that reddened a corpus over an entry written
before it landed is the reading section 4 refuses everywhere else -- whoever
takes this decides what `check` says, if anything, about an entry already in
the files.
