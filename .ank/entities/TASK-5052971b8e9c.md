Recovered from `fix/clone-url-msys-pathconv`, a local branch carrying a measured
fix that was never merged. Its original task, TASK-f5a6848283ed, is `closed`, so
this is a new task rather than a reopening — a closed task was not done, and its
work does not come back by editing its status.

The helper builds `file:///` and then strips the path's leading slash, which on
Windows gives `file:///C:/...`. Unix is unaffected: the path already starts with
`/`, so both forms produce `file:///tmp/...` and agree.

**The variable is the cause, not the git version.** `git.exe` reads
`MSYS_NO_PATHCONV` itself, so it reaches a git spawned with no shell at all.
With the conversion active git accepts `file:///C:/...`; with the variable set
it reads that URL back as the path `/C:/...` and refuses it. Three sessions lost
the suite to this and concluded the git version had changed, which it had not.

The fix on that branch keeps the path whole — `file://C:/...` — which git takes
with the variable set or unset. It is one line, and what is worth carrying over
is the comment beside it: this is a cause nobody deduces twice.

**It is deliberately not in the current wave.** It touches
`crates/ank-cli/tests/cli.rs`, which both binary-lane tasks also touch, and
running it alongside them is what the lane split exists to avoid.
