Measured on 2026-08-16, cutting v0.3.0. The release run was green end to end: the
version gate agreed with the ten literals, the four targets built and tested, the
release page carried its eight files, and npm published 0.3.0 under `latest`.
None of publish-brew, publish-scoop, publish-apt or publish-winget started.

The cause is in release.yml, not in the four. The `publish` job creates the
release with `gh release create` under `GH_TOKEN: ${{ github.token }}`, and
GitHub does not start a workflow run from an event produced by the default
`GITHUB_TOKEN` -- the rule exists to stop a workflow triggering itself. So
`release: types: [published]`, which is the only trigger under which those four
derive and commit anything, never fires. Every other trigger they carry derives
for the version the committed file already claims and asserts it, which is a
correct test of the file and no publication at all: on a workflow_dispatch today,
brew, scoop and winget would have re-verified their 0.2.0 manifests and committed
nothing.

This is the first tag cut since the four channels were added, which is why it was
invisible until now. v0.2.0 predates all of them.

The release was completed by hand: `gh release edit v0.3.0 --draft=true` then
`--draft=false`, run from the maintainer's own token, which produced a real
`release: published` and the four runs that followed it. That is a workaround and
not a fix -- it depends on a human being present at the moment a tag is pushed,
and it briefly makes the published release a draft.

Two candidate fixes, neither measured yet.

A token that is not the default one. `gh release create` under a PAT or a GitHub
App installation token triggers downstream workflows normally. The cost is a
long-lived secret with `contents: write` on the repository, held for the one call
that publishes -- and the `publish` job is deliberately the only job in that
workflow holding write at all.

Chaining inside Actions. `workflow_run` on the completion of `release`, or a
`repository_dispatch` sent by the publish job, both start a run without a second
credential. The cost is that the four workflows would then read their version
from something other than `github.event.release.tag_name`, and the `release`
branch of their derivation -- the one that carries `--require-all` and the commit
to the default branch -- is written around that field today.

Whichever is chosen, the criterion is the same and it is measured on a tag: the
four runs exist, they carry event `release`, and the manifests on the default
branch name the version that was just published.
