A defect against ADR-621a7fd96ce1, which keys a corpus "on its root commit and
never from its path" and names two worktrees of one repository as the case.

Measured on 2026-10-26 at e04c0dad: with a linked worktree of `web` at
`lab/wt-web1`, `ank context src/` there served the local ADR and **dropped
`ADR-71f0e88947fb@api` with no warning at all**; the main checkout still listed
it. Writing the override `peers.<api-id>.web <wt-web1>` bound the worktree and
unbound the main checkout, so N parallel worktrees can never all be bound.

The cause is `Peer::binds` (repo.rs), which ends in `same_corpus(&root,
&reader.corpus)`, a filesystem comparison of the path the peer's declaration
resolves to with the reader's own root. A worktree's root is never that path.
Compare the identity of the corpus the declaration resolves to with the
reader's identity instead; the resolved root still has to be a corpus, so an
entry naming a third repository keeps binding nobody.

Cost: identity is a git process. `peer_root` already asks it only of a reader
with overrides (ADR-f3d1 discipline). Count the git processes `ank context`
spawns before and after with GIT_TRACE on the pair, and record both numbers with
`ank log`.
