Observed on 2026-09-20 on Linux, worktree 5e6a, while closing TASK-5e6aabcddbb0. One run of 'cargo test --workspace' failed a single test:

    test cli::tests::the_foundation_is_resolved_before_the_verb_runs ... FAILED
    error[1]: no .ank/ found from /path/that/does/not/exist
      -> ank init
    error[1]: index: another process is writing the index (database is locked)
      -> re-run the command: the index is a cache and the writer is finishing
    panicked at crates/ank-cli/src/cli.rs:1552: check answered with 1

362 passed, 1 failed. The same test alone passes, and two consecutive full runs afterwards were green (50 'test result: ok' lines, no failures), so it is contention between tests in one binary and not a defect in the verb.

This is TASK-e9dfaf187a1b's family and not its case. That one fixed two processes racing, measured as 'attempt to write a readonly database' and 'disk I/O error', and its test spawns the built binary. What is left is the in-binary shape: several tests on cargo's thread pool opening this repository's own index at once, where the loser is told to re-run a command no test will re-run. A suite that fails once every several runs is a suite whose red stops being read.
