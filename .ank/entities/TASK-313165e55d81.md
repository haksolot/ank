The biggest gap left in v1, and the one that undercuts the tool's own premise.
ADR-6b3f19e08a24 says freezing is verifiable rather than defended: every frozen
field is anchored in an artifact the file's editor does not control. For the
eight ADRs binding this repository that artifact does not exist. They were
accepted by hand during bootstrap, `allowed_signers` declares no key, and
`check` says so on every run:

    signal: allowed_signers: no ratification key declared
    signal: ADR-...: accepted with no ratification commit  (x8)

So the constraints are binding by convention. `accept` exists, is tested, and
has never been used on the corpus it was written for.

**This one needs the human, not the agent.** `accept` produces a *signed*
commit on the default branch, which needs a key an agent has no business
holding, and §8's whole point is that human identity is anchored by something
an agent cannot forge. An agent can prepare everything and must stop at the
signature.

Order matters: declare the key in `allowed_signers` first, or `accept` anchors
against a signer nobody has vouched for.

## Notes carried in the log

allowed_signers declares the real GPG ratification key. Under GPG git never reads that file -- it consults an allowed-signers file only under gpg.format = ssh -- so the entry is a declaration and not a mechanism, and the file says so in its own comments rather than leaving a reader to assume enforcement. Switching the repository to ssh signing would make it load-bearing and was declined: it would change the signature of every commit here, not only the ratifications.

The seven bootstrap ADR are ratified on main, signed, and check reads their anchors back out of those commits and finds them intact. Fifteen signals down to eight: the seven `accepted with no ratification commit` and the allowed_signers one are gone.

One part of the criterion is met on its letter and not on its strongest reading, and it is filed rather than glossed: check reads the anchor from the ratification commit but does not verify that commit's signature. An unsigned commit with the right subject and the right hash would pass. TASK-d31af22248d9 carries it, together with the question allowed_signers raises the moment it stops being decorative.

Also worth recording against my own account: the first accept of the day ran outside this task's claim, on a probe I wrongly assumed was read-only -- accept has no dry-run. It wrote an anchor and a signed commit on main and was undone with a soft reset and a single-path restore. And no signature prompt appeared for any of the seven, because the gpg agent on this machine is unlocked. Section 8 names that exact case in the abstract; it is worth knowing it is not abstract here.
