constraint: |
  A corpus's index lives at .ank/index.db.<N>, N the index schema version of the binary reading it. A binary opens, rebuilds and writes only the file of its own schema and never opens, rewrites or removes another, so two binaries of different schemas on one corpus never rebuild each other's index. A file it creates takes the archived digests from the file of the newest older schema present, so an upgrade does not reset what ank archive's integrity rests on. The unsuffixed .ank/index.db and files of other schemas are left as they are: disposable, and already ignored by the .ank/index.db* line init writes.

Measured during the parallel run of 2026-10-02: TASK-ea86d1cc4af4 moved the
index schema from 10 to 11, while the herdr ank integration kept polling the
binary on PATH, still at 10, in every worktree. Each binary found the other's
version in `.ank/index.db`, dropped every table and rebuilt. The worker's
`ank done` lost the race on its final write, and a test reading the real index
failed about half the time with "disk I/O error". Nothing was wrong with either
binary; they were sharing one file that only one of them could read.

**Why a file per schema.** Every version keeps its own index warm, and no
binary ever opens a file it cannot read. An older binary is not slowed down,
which the alternative (an older binary leaves a newer index alone and answers
from the files) would have done on every poll. The `.ank/index.db*` line init
already writes covers the new names and their WAL files, so no repository has
to change its `.gitignore`.

**The archived digests carry over.** The index holds one thing the files
cannot rebuild: the digest an archived file arrived with (docs/format.md). Today
a schema bump drops it with every table, and so did each round of the fight
above. A new file seeds that table from the newest older-schema file present,
which keeps archived integrity across an upgrade instead of silently resetting
it.

**What is left behind.** Old files are not removed: a binary that deleted
another schema's file would only make that binary rebuild it on its next run.
They are derived and disposable, and whoever wants the space deletes them.

SPEC-7edbdf871408 names `index.db` in the layout; its successor carries this
decision.
