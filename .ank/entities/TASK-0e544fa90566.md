Follow-up to GitHub #495, points (2) and (3). Measured in a herdr pane on a corpus whose config.yml repeats 'verifiers': after the refused find, the header reads 'the corpus has not been read' and the entity panel '(0 in the corpus)' over 'no entity matches this filter' -- an empty corpus and a filter that were never there. The first frame, before any read, draws the same panel. The claims and queue panels already answer the same question with '(not asked)' (TASK-fff0a98511b2); the entity panel is the one that answered with a count. Three states: not read, could not be read, read. A refused reread over a corpus already read keeps the rows it had, and is out of scope.
