Re-filed with the reproduction the closure of TASK-c04889b7f21f asked for, and
with nothing else: the earlier reports blamed this URL form from a red suite
under four concurrent `cargo test --workspace` runs, which is not a measurement.
This one is.

`clone_of` builds its URL as `format!("file:///{}", path.replace('\', "/")
.trim_start_matches('/'))`. On Linux the path starts with a slash, the trim
removes it, and the result is `file:///home/...` — three slashes, correct. On
Windows the path starts with a drive letter, there is nothing to trim, and the
result is `file:///C:/Users/...` — three slashes then `C:`, which this git parses
as the path `/C:/Users/...`.

Measured on git 2.54.0.windows.1, on a short path under `%TEMP%`, with no
`protocol.file.allow` and no `safe.directory` set anywhere, and with MSYS
argument conversion disabled so git receives the string as written:

    git clone -q "file:///C:/Users/seanl/AppData/Local/Temp/probe-src" d1
    fatal: '/C:/Users/seanl/AppData/Local/Temp/probe-src' does not appear to be
    a git repository
    exit=128

    git clone -q "file://C:/Users/seanl/AppData/Local/Temp/probe-src" d2
    exit=0

And through the suite rather than through a shell, which is where it matters:
at e1f0b18, in a clean worktree of that commit with no other change in the tree,
`cargo test --test cli -- a_shallow_clone_cannot_explain_a_dead_scope` fails in
3.15 seconds with the same message, as the only test running. It is not
load-dependent here and it does not need the rest of the suite to reproduce.

Two slashes is the form that works on this machine, and the fix has to keep
Linux and macOS working — `--depth` is ignored on a local path clone, which is
why the fixture uses a URL at all, so the URL cannot simply become a path.
