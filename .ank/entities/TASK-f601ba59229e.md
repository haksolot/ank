Found by running the tool, not by reading it. In a sandbox of two clones and two
worktrees, `ank claim` refused a task finished on another branch and offered
this:

```
error[4]: TASK-1e154c82816e finished on another branch (commit ed45c00, branch feat/delta), not merged here yet
  -> ank claim TASK-077b9e032ef2   (another ready task in this scope)
```

`TASK-077b9e032ef2` was held by another agent, its ref was in this clone, and
the same listing rendered it `[claimed:agent-a2/1]` one command earlier. The
hint printed an exact command that refuses with code 4 the moment it is run.

The rule it breaks is stated in the code that breaks it. `other_ready_task`
carries a doc comment saying a candidate with a completion ref is skipped
because offering it would print an exact command that refuses the moment it is
run, which is the generic help by another route. The predicate below matches
`Record::Completed` and nothing else, so a live `Record::Claim` walks straight
through. It is the same failure, one ref state over.

Section 7 states it for the whole surface: the task offered as another thing to
take is one whose ref is free, not one whose file reads `open` on this branch
only because something has not landed yet. A live claim is that case exactly.

A lapsed claim is not, and the fix must keep offering it. Pickup after expiry is
a legal transition, `claim` takes it, and skipping it would trade one wrong
answer for another. The predicate is therefore a claim record that has not
expired, which is the reading `is_expired` already gives everyone else.
