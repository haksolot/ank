TASK-3e68786fa443 made the kind reachable: `new spec` creates, `show` reads
whole, `find --type spec` lists, `context` names it beside the constraints and
never quotes it. What it deliberately did not touch is the half of the lifecycle
that costs a signature, and this is that half.

Three arms in `crates/ank-cli/src/human.rs` still say so out loud, and each is
honest today rather than wrong:

- `accept` resolves an ADR and refuses anything else by name, so a spec is
  created `proposed` and has no way to leave it.
- `amend` refuses a spec with code 7, naming the kind. A spec has no
  `blocked_by` and no `done_criteria`, so what it could carry is a scope change,
  under the same rule an ADR's is under: allowed while `proposed`, refused once
  the scope is anchored in the ratification commit.
- `check` runs what every kind owes -- the scope, authorship, readings -- and
  has no per-kind arm for a spec, so the freeze it cannot yet acquire is not yet
  verified either. `repair` names no command for a dead scope on a spec, which
  is right precisely until `amend` reaches one.

**The anchor is the one place a spec differs from an ADR** (§3): `ratified`
holds the hash of the **body and scope**, because there is no narrower field
carrying the authority. An accepted spec whose body has moved is altered, on the
same terms and by the same walk as an ADR. The consequence is deliberate and is
the doctrine applied rather than an exception to it -- revising an accepted
specification is a supersession, and a working draft stays `proposed` while it
is one. `--supersedes` already resolves inside one kind, so the chain a spec
declares is a chain `accept` will be able to complete.

Nothing here changes what `context` does with a spec. It is named and never
quoted whatever its status, and an altered spec has no constraint to suspend --
the suspension an ADR gets exists to stop an edited rule from binding, and a
spec binds nobody.
