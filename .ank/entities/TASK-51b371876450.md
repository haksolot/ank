Found by running the thing. `ank accept ADR-4e7c25b1f639` exits 6 with
`illegal transition: accepted -> accepted`, and so do the six others, because
`AdrStatus::transition_allowed` (model.rs:98) admits only `Proposed ->
Accepted` and `Accepted -> Superseded`. The seven ADR that bind this repository
were written `accepted` by hand during bootstrap. They never passed through
`proposed`, so `accept` has no door to them at all.

`check` already names the state exactly -- `accepted with no ratification
commit (bootstrap, or accepted by hand)` -- which is the tell: the condition was
foreseen and the remedy was not built. TASK-313165e55d81 cannot be done until it
is, and its scope is `.ank/` only, so this is a separate task and not a widened
one.

Two locks, not one.

The first is the transition. Ratifying is not re-accepting: what is missing on
these seven is the anchor, not the decision. The condition that carries the
whole weight is `ratified.is_none()` -- an ADR that already has an anchor must
keep being refused, because `accept` on an accepted ADR is otherwise a way to
edit a constraint in place and then re-anchor it, which is exactly the property
ADR-6b3f19e08a24 exists to hold. The refusal is the feature; the exception is
narrow and must be argued in the message.

The second is the succession. ADR-63b59c5c26f7 and ADR-b8884edcebe3 name a
`supersedes` whose target is already `superseded` -- performed by hand, like the
acceptance. `superseded_target` (human.rs:1222) refuses any target that is not
`accepted`, which is right for a fresh succession and wrong for one already
recorded. The discriminator is not the status alone: it is whether the target's
`superseded` state is attributable to *this* ADR, which is the same question
`check_adr` answers in its reverse direction. Target superseded and named by
this ADR means the succession exists and there is nothing to write. Target
proposed means it was never binding, and that stays a refusal.

Not a format change, so ADR-63b59c5c26f7's ordering does not bind here, but the
specification describes the verbs and would be wrong the moment the code lands.

The test has to reach the commit. Two `accept` tests were green for months over
a promotion that never happened, because both asserted refusals and neither ran
past the branch check -- the defect surfaced only when a test finally wrote a
commit. A refusal test proves nothing about the write path.

## Notes carried in the log

The condition carrying the weight is `ratified.is_none()`, not the status. Ratifying is not re-accepting: an ADR that already carries an anchor stays refused, because `accept` over an existing anchor is exactly how a constraint edited in place would be re-anchored, which is the one property ADR-6b3f19e08a24 exists to hold. Supplying a first anchor launders nothing -- there is nothing for it to diverge from. The refusal names `ank new adr --supersedes` and not the file, because changing a ratified decision is a succession.

The claimant scan moved before the status match, and that reordering is the design and not tidying. A target reading `superseded` is either this ADR's doing or somebody else's, and the status alone cannot say which; only the absence of another accepted claimant makes the succession attributable here. The same condition covers a state I did not set out to handle: an `accept` interrupted between its two writes leaves precisely that corpus, so resuming it is the bootstrap case and needs no separate code.
