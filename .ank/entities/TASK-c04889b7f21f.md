`clone_of` builds its URL as `format!("file:///{}", path)` (crates/ank-cli/tests/cli.rs,
around line 7621). On Windows that yields `file:///C:/Users/...`, and git
2.54.0.windows.1 refuses it: it strips `file://`, keeps the leading slash, and
reports `'/C:/Users/...' does not appear to be a git repository`. Every test
going through `clone_of` dies at the `r.git(&args)` assertion in the harness,
which today is `a_shallow_clone_cannot_explain_a_dead_scope_and_says_so_instead_of_faulting`.

Measured side by side, on real Windows paths, with `--depth 1`:

  file://C:/Users/.../src        clones, and writes .git/shallow
  file:///C:/Users/.../src       fatal: does not appear to be a git repository
  file://localhost/C:/.../src    fatal: does not appear to be a git repository
  C:/Users/.../src               clones, and warns `--depth is ignored in local
                                 clones; use file:// instead`

So the third slash before the drive letter is the whole defect, and the last line
confirms the helper's own comment: dropping the URL for a path would silently
turn the shallow fixture into a whole one, which is the failure the comment
exists to prevent. The fix is the URL form, not the mechanism -- emit two slashes
before a drive letter and three before a POSIX path, where `file:///home/...` is
already correct because the path carries its own leading slash.

Why this is latent rather than merely broken. CI is green on all three platforms
for the run that merged the test (run 31727213678, PR #111), so the
windows-latest image still carries a git that accepts the three-slash form. The
suite turns red on its own the day that image updates, on a commit that changed
nothing -- which is the expensive way to find this. It is already red on a
developer machine running git 2.54.
