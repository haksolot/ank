Measured on 2026-08-27, after this suite OOM-killed the host twice.

`/tmp` on the development host is a RAM-backed tmpfs with no swap. 8361
abandoned fixture directories were found in it, 1.1G of unreclaimable memory:
5002 `ank-cli-it-*` (663M) and 3359 `ank-watch-it-*` (479M). The machine has
7.8G. The OOM killer took `herdr.service`, and with it every agent pane running
under it, twice in ten minutes.

That the host mounts `/tmp` on tmpfs is the host's business and not this
repository's. That a green test run leaves 479M behind is this repository's.

## Three leaks, and only one of them is the obvious one

**The unconditional one.** `watch.rs::scratch()` returns a bare `PathBuf`, and
`Home(PathBuf)`, which is what wraps it, has no `Drop`. `Running`'s `Drop` kills
the daemon process and says nothing about the directory. So every one of the 21
`scratch()` call sites leaks on **every run, including a green one**.
`tui.rs::scratch()` has the same shape.

**The unowned one.** `cli.rs:52` writes a shared gitconfig at a fixed path per
pid and nothing ever removes it; `cli.rs:2238` creates `ank-cli-it-nowhere` at a
fixed path shared by every run at once.

**The circular one.** `cli.rs`'s and `tui.rs`'s `Repo` *do* implement
`Drop { remove_dir_all }`, and on an ordinary run they clean up correctly. Their
5002 directories came from runs that were **killed**: no destructor runs on
SIGKILL. So the leak filled memory, memory pressure killed the tests, and the
killed tests leaked — the failure fed itself.

## Why the fix cannot be another destructor

The third leak is the argument for the shape of the criterion. A `Drop` impl is
the right thing for a green run and is worth keeping, but it is unreachable in
exactly the case that produced most of the garbage. Cleanup that only ever runs
forward can only ever be best-effort.

A per-process root plus a sweep of dead predecessors is the property that
survives a kill: the run that cleans up is the next one, which is always alive
by definition. It also collapses the four naming schemes into one place, so
"what does this suite leave behind" stops being a question with four answers.

`std::process::id()` is already in every one of those names, so the pid the
sweep needs is the one the directory is already called after.
