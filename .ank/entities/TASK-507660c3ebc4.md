Rests on ADR-964be4d940b2, which is proposed and binds nobody until it is
ratified. Do not start this before it is accepted: it is the decision, and this
is its consequence.

`accept` runs `git commit -S` unconditionally (`human.rs:4319`) and exits 9
naming `git config user.signingkey <key>` when signing fails. `check` mean-
while has an advisory mode §8 defines: no key declared, no signature judged. So
a corpus in that mode cannot produce a ratification at all, and nobody chose
that -- it is an asymmetry between two halves written at different times.

**The whole difficulty is the second half of the criterion.** Making `accept`
stop refusing is small. Making a corpus say which regime it is in, on every
surface, without ever letting the unsigned one read as the signed one, is the
work. §8's existing rule is the model: a signature present with no local public
key is a signal and never a pass, because a verification that degrades to
success is not a verification.

`review` already names who may ratify (TASK-8a80b590b356), which is where a
reader looks for this.

**The specification is superseded, not amended.** "Ratification requires a
signed commit" is in the body of SPEC-199de7ac4730, and the body of an accepted
spec is hashed into its ratification commit (§3), so there is no edit to make.
The succession is part of this task and is written last, against behaviour that
exists.
