During v1 development the agents kept re-reading docs/ank-spec-v1.1.md whole: a ~1000-line document with no routing, so working on exit codes also loads synchronisation and permissions. The tempting fix is a 'spec' entity type served by 'ank context' like constraints are.

Rejected for now, for three reasons:

1. A spec's authority comes from being one coherent document. Its sections are not independent the way ADRs are: section 4 refuses on state because section 8 makes roles advisory; section 7 only makes sense with section 3. Fragmenting it into scoped entities creates drift between fragments - the exact failure the single document prevents.

2. Ank already has the right sink for what grows. Section 11's model: a rule born in prose becomes either a scoped ADR (served by context) or a mechanised check (goldens, CI, enforced_by) once it binds daily work. What remains in the spec is narrative and rationale, read when designing, not when executing. Narrative does not need routing.

3. Section 10 already defers additional entity types with 'Do not anticipate'. The common base makes the extension trivial later; the signal to act is repeated pain that ADRs cannot absorb, not an intuition.

The available remedy today: when the same spec section keeps being reopened for a given perimeter, distil it into a scoped ADR that summarises it and points at the section. The spec stays the authority; the ADR becomes the context vehicle.

This task exists to record the idea and its trigger where section 10 records every other deferral. Do not implement the entity type under this task; if the trigger ever fires, that is a new task plus a spec revision.
