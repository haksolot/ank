`release.yml` derives the published version from `$GITHUB_REF_NAME` and from
nothing else. Nothing compares it with the version compiled into the binary.

So a tag pushed without bumping the manifests produces an archive named
`ank-0.2.0-x86_64-unknown-linux-musl`, an npm package published as `0.2.0`, a
GitHub release titled `v0.2.0` — and a binary inside all three that answers
`ank 0.1.3`. Every artefact agrees with every other artefact and all of them
disagree with the thing they contain.

The existing smoke job does not catch it, and it is worth being precise about
why, because at a glance it looks like it should. It compares
`"$direct" --version` with `npx ank --version`, deliberately "against the
artefact itself rather than against a literal, so the assertion cannot drift
from the version it ships". That makes it a correct test of the wrapper and a
test of nothing at all here: both sides read the same binary, so both are
equally wrong when the manifest is stale.

This is the same defect the `msrv` job exists to prevent one level up, and the
same reasoning applies to it: a number in two places is a number that will
disagree with itself, and the fix is to make the disagreement fail rather than
to be careful. Nine literals across seven files carry it today, which is eight
more chances to be careful than anyone gets right forever.

It must run before the build, not after: the point is to refuse to publish, and
a check that runs at the end has already spent the matrix.

Note the one legitimate asymmetry. `npm-assemble.sh` stamps the version into the
npm manifests at release time with `npm pkg set version=`, so those files are
overwritten by the run rather than read by it. They are still worth comparing:
the tree is what a reader sees between releases, and a tree that says `0.1.3`
while `latest` is `0.2.0` is the same lie told to a different audience.
