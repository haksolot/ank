`.ank/` should be as opaque to an agent as `.git/` is. Nobody opens
`.git/refs/heads/main` to read a branch; they run `git rev-parse`. The reason is
not secrecy, it is that the tool knows things the file does not: the budget of
§5, the truncation notice, the freeze, what is claimable and by whom.

**The instruction currently says the opposite, in as many words.** SKILL.md:

    Read the entity file when you want the whole body. The format is the
    specification and `cat` is your `show`; the CLI is not the only way in.

An agent that follows the file it was given reads `.ank/` directly, and is
right to. That line goes first, or everything else here argues with it.

It was defensible when written and is not any more. `ank show <prefix>` returns
the entity byte for byte, frontmatter and body, for tasks and ADRs alike;
`ank find --status open` lists without needing a query; `ank context` serves the
constraints in full and says so when it truncates. Measured on 2026-07-31: not
one read of an entity requires opening a file. The write side was the real gap,
which is why this task is blocked on the two that close it rather than filed
alone.

The claim in CLAUDE.md that `.ank/` is "maintained by hand for as long as the
CLI cannot do it" is the same sentence read from the other end. Once the CLI
can, the clause has to go, or it stays a standing permission nobody revisits.

Three layers, and they are not redundant. The ADR states the rule where
`ank context` will serve it to every agent at the top of every session -- the
mechanism this project built for exactly this. SKILL.md stops contradicting it.
The hook is what actually refuses, because a constraint an agent can read is a
constraint an agent can forget, and §5 was never going to be enforced by good
intentions.

**The hook does not make ank a gatekeeper.** ADR-6b3f19e08a24 says no frozen
field may rely on the CLI refusing a write, and nothing here changes that: the
freezes stay anchored by hash and stay verifiable by anyone. What is being
constrained is the agent's harness, not the tool. A human with an editor keeps
every power they had; `check` remains the thing that notices.

Proposed, not accepted. §8 and the `roles` block of `config.yml` both say an
agent may write `new:adr:proposed` and never `adr:accept` -- the acceptance is
the human's, and TASK-313165e55d81 is what makes it mean something.
