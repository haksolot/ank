The claim record carries two hashes: the frozen done_criteria and a hash of the
set of constraints applicable to the task scope at claim time
(ClaimRecord, claim.rs:158-172). Section 7 says exactly what the second one is
for: it closes the long-work window, because a constraint accepted while the
agent works changes that hash, and done WARNS - never blocks, since a new
constraint does not necessarily concern work already finished - inviting a
re-read of ank context. check reports the same case.

Half of that is true. check does report it (human.rs:667-676). done never reads
ClaimRecord.constraints at all; it verifies the criteria freeze and nothing else
(done.rs:143). So the field is written at every claim, carried for the whole life
of the ref, and consulted only by a verb the agent is not required to run.

The window this leaves open is the one the design already judged worth closing:
an agent claims, works for an hour, a constraint covering its scope is accepted
meanwhile, and done completes in silence. The agent never learns there is a new
rule over the files it just touched. The warning is cheap - the hash is already
in hand, the constraint set is already computed for that scope by the same code
path context uses - and it is the difference between the mechanism being real
and being decorative.

Two things the implementation must not get wrong:

- It warns, it does not block, and the wording says why the agent should care:
  a constraint landed after the claim, over this scope, re-read ank context.
  Blocking would punish work that predates the rule, which is the case the spec
  singles out.
- The criterion talks about the binary, so the test drives the binary: claim a
  task, accept a constraint covering its scope, run done, assert the warning is
  on the output. Asserting that a hash comparison function returns false proves
  nothing about the path done actually takes - that is precisely how two earlier
  defects in this repo passed green unit tests.
