Left open by TASK-03eaa26bddd1, deliberately and in writing rather than in
silence. `check` now locates the ratification commit by walking the ADR's file
history and compares the `constraint+scope` hash in its message against the
file. What it does not do is ask whether that commit is signed.

The hole is small and complete. Edit a constraint, then make an ordinary
unsigned commit touching the same file whose subject is `ratify <id>` and whose
body carries the new hash. `rev-list` finds it first, the subject matches, the
hashes agree, and `check` reports the freeze intact.

Against the threat model of section 1 -- drift, not an adversary -- that is
arguably tolerable: nobody writes that commit by accident. But section 8 does
not rest on section 1 here. It says ratification *is* the signature, that
`check` verifies it through `git verify-commit` against `.ank/allowed_signers`,
and that human identity is anchored by something an agent cannot forge. An
anchor read from a commit nobody checked the signature of anchors nothing
against the case the whole mechanism exists for.

The awkward part is what to do when verification cannot happen, and it is why
this was not folded into the previous task. This repository signs with GPG, so
`git verify-commit` resolves through the keyring; a clone on a machine without
the public key cannot verify a commit that is perfectly signed. That must not
read as a fault -- CI would go red on a correct repository -- and it must not
read as success either, or the check disappears exactly where it matters. It is
a third answer, next to the `cannot verify` that TASK-03eaa26bddd1 already
introduced for an unreachable commit, and the two are not the same state.

`allowed_signers` also stops being decorative the day this lands: under GPG git
never reads it, so either `check` parses it itself to decide which keys count,
or the file goes on declaring something nothing enforces. That choice is part of
this task.
