discover walks parents until it finds a .ank/, and its stopping condition is
dir.parent() returning None - the filesystem root (repo.rs:38-48). It never
consults .git, never stops at a repository boundary, never mentions which root it
settled on.

From root/repoA/src/, with no repoA/.ank/, the walk continues into root/.ank/ and
the verb runs there without a word. That is a coin with two sides:

- It is what would make an umbrella corpus at the root usable at all: one .ank/
  covering several checkouts, scopes written as repoA/src/**, reached from
  anywhere below. Nothing was designed for that, but nothing forbids it either.
- It is also the quietest possible way to work in the wrong corpus. And the
  failure is not symmetric with reading the wrong file, because claims are git
  refs: they land in the git repository of the resolved root, which in that
  layout is the outer one, not the repository whose code is being changed. The
  coordination plane and the code part company, silently.

Worth noting the resolution order is otherwise deliberate: the repo is resolved
before the git check specifically so a bad --repo is reported as a bad --repo
rather than disguised as an environment problem (cli.rs:881-886). The same care
has not been applied to a walk that succeeds at the wrong place.

Candidate answers, cheapest first:

1. Say nothing more, but make it visible where it already costs nothing:
   ank status prints the branch and the default branch; the resolved root belongs
   in the same breath.
2. Warn once when the resolved root is not inside the same git repository as the
   working directory. Degrade, do not fail - the walk still succeeds.
3. Decide silence is correct, because --repo exists for the ambiguous case and a
   warning would fire constantly in the umbrella layout above, and record that.

Related: TASK-35df68dd0eb3, which records multi-repository federation as
deferred. This finding is the accidental half of that question, and it is
actionable on its own.

Three design points the task left open. The warning fires only on the walk, never on an explicit --repo: that is what answers candidate answer 3, since the umbrella layout says which corpus it means once and is then never warned again. It goes to stderr, because ADR-0c8a requires --json to stay byte-for-byte what a parser reads and this is not part of any verb's answer. And the comparison is on 'rev-parse --git-common-dir' rather than --show-toplevel, because a linked worktree has a toplevel of its own but shares refs/ -- comparing toplevels would warn about a layout where the claim plane is in fact shared.

Found a gap wider than this task and left it: the specification never describes the discovery walk at all. repo.rs is headed 'Repository discovery (section 6)' and section 6 covers the storage layout, atomic writes, the index and the three levels of search -- nothing about walking up to the nearest .ank/, and --repo appears only in the global flag list. So there is no spec text this change contradicts, and none it could have been written against. Filed separately.
