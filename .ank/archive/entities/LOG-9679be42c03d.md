The pool is a function of the releases and nothing else. Every run rebuilds it entire from every published non-prerelease carrying a musl archive, and the Pages deployment replaces the whole site, so no state survives between runs and there is nothing to drift. A release yanked on GitHub leaves apt at the next publish. The cost is one download per release per run -- five today; that is the number to watch, not a problem to solve now. This is also why there is no "the committed file is the derivation" job here as there is for brew and scoop: their derived files are committed and can be edited by hand, this tree is built and published in the same run and never exists in the repository at all. Exactly one file is committed, packaging/deb/ank-archive-keyring.asc, and the script refuses when the key it signs with is not that one -- a rotated secret with a stale public half would otherwise fail only on a user's machine.

Which key signs is decided by the event, and a release may not fall back. APT_GPG_PRIVATE_KEY is the distribution key; when it is absent -- a pull request from a fork, where secrets are not exposed -- the script generates a throwaway key so the mechanism stays testable, because what those runs test is an apt client fetching a key and refusing an index it cannot verify, and a throwaway key exercises that exactly. APT_REQUIRE_KEY=1 refuses the fallback and the workflow sets it on the release path: a published tree signed by a key nobody trusts is worse than a publish that failed.

apt-ftparchive must not write its Release through a redirection. The shell creates the empty file before the scan, so apt-ftparchive lists Release among the files it checksums, with the size and hash of the empty file it is about to become. apt reports that as a hash mismatch on the index it just downloaded and the cause appears nowhere in the message. Written to a temporary and moved.

The install job carries a negative control and it runs before the key is installed: adding the repository with no key must make apt-get update fail, and fail naming the signature rather than a 404. Signing buys exactly one thing, and a job that only ran the happy path would pass just as well against a repository signed by nobody.

amd64 only, and that is a fact about release.yml rather than a decision here: the matrix builds no aarch64 Linux target, so a repository claiming arm64 would claim a package it cannot serve.
