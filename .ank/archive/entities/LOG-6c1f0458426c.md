 (scratchpad repro.sh). Default wall (5s): refused 0 of 40. ANK_INDEX_BUSY_MS=100: refused 35 of 40, every one with the Windows message verbatim. Instrumented with a probe at both IMMEDIATE begins: every refusal is refresh's BEGIN IMMEDIATE (Index::refresh_counted), waited=100.6-100.7ms (the busy handler ran the whole wall), DatabaseBusy extended code 5; ensure_schema's begin never refused. The single winner held the write lock 538-568ms to write 3184 rows. Cause: the busy handling the readers rely on is one fixed wall, sqlite3_busy_timeout(5s) set in try_open, and SQLite's busy handler on Windows (winSleep loop, same as unix) does exactly what it does on Linux: wait up to the wall, then answer SQLITE_BUSY. Losers re-read under the lock and write nothing (TASK-b9701a228f47), so each waits exactly one writer's hold; the wall is independent of how much that writer has to write, so a runner where a 3184-row cold rebuild holds the lock past 5s (the failing attempt took 21.8s overall) refuses every reader that queued early. Not Windows-specific SQLite behaviour: Linux refuses identically once the hold exceeds the wall, which the knob stages.
