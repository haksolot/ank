 update-ref with no lock timeout, and git's default is to fail at once rather than wait for the loose-ref lock. Control, with a .lock file held by hand on the ref being written: git update-ref returned 'cannot lock ref ... File exists' after 157 ms, and the same command under -c core.filesRefLockTimeout=5000 returned the same message after 5700 ms, so the flag is what turns an instant refusal into a bounded wait. Through the binary with the same lock held, ank claim now takes 5379 ms before it reports, where it used to report at once; under real contention the holder releases in microseconds and the wait ends in the compare-and-swap it was queued for, which is the exit 4 the criterion asks for. Both writes of refs/ank/ carry the flag, claim.rs::update and delete_at, and those two are the only update-ref calls outside tests in crates/ank-cli/src. Process count: GIT_TRACE at an absolute path counts 10 built-in git processes for one ank claim, the same as before, because -c is consumed by the git wrapper and spawns nothing; the trace prints the update-ref line without it, which is why the flag cannot be read back out of a trace and is measured by the wait instead. cargo test --workspace exit 0, cargo fmt --check exit 0. The runner that found this, x86_64-apple-darwin, is in no ci.yml matrix, so the release rehearsal is the proof that remains to be run.
