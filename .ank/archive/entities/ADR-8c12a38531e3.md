## Context

Measured on CI runs 38373336710 and 38279153781 (2026-10-13): the Windows test
leg takes 14 to 16 minutes and sets the time of every run. Compilation is under
2 minutes; about 13.5 minutes is test execution, because `cargo test` runs the
71 integration binaries one after another. `tests/cli.rs` alone takes 407s on
Windows, against 36s on Linux. `ank done` runs the same suite through the
`cargo-test` verifier.

nextest runs every test of every binary from one pool, one process per test, so
binaries no longer wait for each other.

## Decision

1. The `cargo-test` verifier and the CI `test` job run `cargo nextest run
   --workspace`. Doc tests are not run by nextest; the workspace has none
   today, and one added later needs `cargo test --doc` beside it.
2. **Missing runner, exit 9.** `cargo nextest` absent makes cargo exit 101,
   which `done` would report as a failing test (code 5). The verifier checks
   for the runner first and exits 9, the environment code of SPEC-fe67fbaa2708.
3. **Serialisation by test group.** Six files under `crates/ank-tui/tests/`
   serialise through `static ONE_AT_A_TIME: Mutex`. With one process per test
   that lock serialises nothing; a nextest test group with `max-threads = 1`
   carries the constraint instead.
4. **Installed from the published binary**, pinned, with no third-party
   action, which keeps the choice the workflow already makes for its cache.
5. The job names, and so the six required checks, do not change.

## Consequences

- A contributor installs cargo-nextest once; CONTRIBUTING says how.
- The count of tests must be equal under both runners, measured when the
  change lands, so no test is silently dropped by the switch.

## Rejected alternatives

- Sharding the Windows leg across jobs: adds required checks, and multiplies
  compilation, which nextest does not.
- nextest in CI only: `done` would keep paying the sequential cost the change
  removes, and the verifier and CI would run the suite two ways.
