 migrated correctly, which is the defect worth recording because it is the mirror of the one the criterion is written around. It asserted the count over the whole corpus: 512 lines read from 178 files, 514 entries found afterwards, and the two extra were entries this session had already written as entities before the move ran. The verb had already removed the files it read by the time it counted, so it exited 1 over a tree that was right, and a caller trusting the exit code would have reverted a good migration. Three changes: the count is per subject and relative to what that subject already carried, the verification runs before anything is removed rather than after, and every line is looked for by its timestamp, author and message together rather than by a count alone, since a count passes on a migration that wrote one entry twice and lost another. A run is also idempotent now: the ids are derived from the line, so a second run recognises what the first wrote instead of refusing it, which is what makes an interruption between writing and removing recoverable. Verified after the fact against git HEAD through the CLI: all 177 tracked files and 510 lines are present, byte for byte, and ank check exits 0 with no fault.
