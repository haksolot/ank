Steady state, warm cache, this repository, 1024 entities and 95 refs, gix 0.86 against git 2.x, all times from Rust and not from a shell:

  open repository      library 53 ms    binary 37 ms
  read 1024 blobs      library 424 ms   binary 990 ms
  read 95 refs         library 3.4 ms   binary 56 ms
  total                library 480 ms   binary 1083 ms

So the library is about 2.3x faster on these reads and saves roughly 600 ms of the 7 s check costs. Eight to nine percent, not the 2.5 to 3 s I argued for.

Two corrections to my own earlier claims, both in the same direction. The 146 ms I measured for git --version was taken from a bash loop and is inflated by the shell: from Rust the same call costs 29 to 40 ms, so 24 processes are about 1 s of spawn cost and not 3. And gix does not open for free either, 53 ms against 37 for a rev-parse, which eats a tenth of what it saves.

The refs are where the library wins outright, 3.4 ms against 56, fifteen times, but 53 ms is not what anyone is waiting for.

And the finding that matters most for sequencing: TASK-2ba2619b90e2 removes most of those blob reads altogether, since the comparison it replaces them with needs object names rather than contents. The two tasks compete for the same seconds. Done in that order, the library would be left with the refs and roughly 50 to 100 ms to win, and the ADR would be arguing for a large dependency and a wide rewrite against a tenth of a second.

Two things this has not measured: Linux and macOS, where a git spawn costs about 5 ms and the gap should be smaller still, and the name-status reads of history, which I did not attempt through gix.

Also recorded because an ADR would have to carry it: gix cannot enter this workspace at all while serde is pinned at =1.0.210. gix-date pulls jiff, which requires serde 1.0.221. That is why the spike is an excluded crate with its own lockfile.
